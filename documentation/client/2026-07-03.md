Anotaciones y directrices recopiladas durante la sesión con el cliente:

* **Tarjetas NFC/QR**: Las tarjetas solo llevan al menú web principal del restaurante. No se requiere guardar un registro de tarjetas en base de datos ni mantener códigos únicos para ellas. Ambas tecnologías (NFC y QR) usarán el mismo link.
* **Mesas**: No dividimos el modelo por mesas. Las tarjetas dirigen directamente a la web general del restaurante, nada más.
* **Categorías**: Deben funcionar como etiquetas (tags), no como contenedores cerrados. Un producto puede pertenecer a más de una categoría (ej. un chuletón es "Segundo plato" y "Carne de vacuno").
* **Estructura de Menú**: 
  - Un menú debe ser un producto en sí mismo, hecho de productos (herencia de producto / patrón composite).
  - Debe soportar menús con opciones de selección (ej. elegir 1 primero, 1 segundo) y menús sin opciones (productos fijos).
  - Se debe poder añadir un suplemento de precio para opciones premium dentro de un menú (ej. +3€ por elegir entrecot).
* **Stock de Menú**: El stock se gestiona en cada producto. Si una sección de un menú se queda sin ninguna opción disponible con stock, el menú completo pasa a considerarse agotado (propagación en cascada).
* **Ingredientes Personalizados**: 
  - Las cantidades y límites de un ingrediente se modelan agrupadas en una clase de objeto de valor (Cantidad) que contiene la cantidad por defecto, mínima, máxima y su unidad de medida.
  - Esto unifica si el ingrediente es opcional (mínimo = 0) o si se puede añadir extra por un precio (máximo > defecto con suplemento).
* **Traducciones**: No se deben modelar como una clase o entidad en el diagrama de dominio. Es un detalle técnico de localización/tabla de base de datos.
